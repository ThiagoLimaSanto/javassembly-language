# IROptimizer benchmark

Run from the repository root:

```sh
benchmarks/optimizer/run.sh 50 100
```

The script compiles the current compiler sources and this harness into a
temporary directory, then runs eight deterministic synthetic IR workloads at
the supplied sizes. If sizes are omitted, it uses `100 250`. Redirect stdout
to save a CSV:

```sh
benchmarks/optimizer/run.sh 50 100 250 > benchmarks/optimizer/results.csv
```

The timed operation is exactly `new IROptimizer().optimize(input)` on the
same prebuilt `IRProgram`; IR construction, CFG counting, JVM warmup, and
correctness comparison are outside the timed interval. Each workload gets 5
warmups and 9 measured calls. CSV reports median, median absolute deviation
(MAD), minimum, maximum, input/output instruction counts, input CFG block
count, and whether repeated calls produce identical final IR. Heap usage is a
single used-heap snapshot after the calls, not peak allocation.

Workloads cover many blocks, temporaries, copy chains, constants across
blocks, loops/backedges with multiple incoming edges, arithmetic, dead
stores, and calls. Inputs are generated by the harness and remain identical
between baseline and future runs of the same size/scenario.

The optimizer does not expose pass counters. Therefore CFG rebuild count,
optimization rounds, and the internal iteration counts of constant
propagation and dead-store elimination are deliberately `not_instrumented`.
Obtaining exact values would require temporary instrumentation or a
non-production Java agent that instruments method/loop boundaries; reflection
cannot observe loop iterations. The harness does not replay passes manually.

For an environment record, capture alongside the CSV:

```sh
java -version
uname -a
printf 'JAVA_OPTS=%s\n' "${JAVA_OPTS:-<default>}"
```
